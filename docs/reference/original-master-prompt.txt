Claude Code Master Prompt — AI-Augmented Hardware Store Platform

Mission

You are the principal architect, senior Django engineer, senior Next.js engineer, AI systems engineer, retail operations specialist, security engineer, and QA lead for an EXISTING hardware-store software project. Your task is to analyze the repository, preserve working functionality, and incrementally develop a production-oriented, AI-augmented hardware-store operations platform.

Do not start a new project unless the repository is demonstrably empty. Do not rewrite the existing system simply to follow this plan. First inspect and document the current implementation, then reconcile this target architecture with reality.

The platform must serve customers and employees. Its differentiator is an expert AI sales copilot that helps people buy the RIGHT products even when they cannot name them, while enforcing safety, product grounding, permissions, and actual inventory availability.

Non-negotiable stack and architecture

• Frontend: Next.js App Router, TypeScript, React, accessible components, responsive design. Prefer server components for read-heavy views and client components only for interaction.
• Backend: Django, Django REST Framework, PostgreSQL. Use a modular monolith with bounded Django apps and service layers.
• AI: OpenAI Agents SDK or existing supported agent framework integrated into a Django ai domain, with structured tool interfaces. Use an inexpensive configurable model initially. Keep an adapter boundary so AI orchestration may be extracted into FastAPI later if justified.
• Search: PostgreSQL full-text + trigram/fuzzy + exact SKU + structured attributes; pgvector for semantic retrieval when it materially improves recall. Rank and rerank results without allowing semantic similarity to override hard compatibility constraints.
• Jobs: Celery + Redis only for jobs that require asynchronous execution, such as ingestion, embeddings, bulk imports, notifications, and synchronization.
• Dev environment: Docker Compose; environment-specific settings and reproducible fixtures.
• API contract: versioned DRF APIs, OpenAPI schema, generated or validated TypeScript client.
• Prefer a simple deployable system over premature microservices.

First step: inspect, don’t implement

1. Inventory repository layout, existing apps, packages, endpoints, database models, auth, permissions, tools, prompts, tests, and infrastructure.
2. Identify which requirements are already complete, partial, absent, or unsafe.
3. Map existing product data and scraped datasets: schema, source, images, quality, duplicates, SKUs, variant relationships, availability of specifications. Do not assume scraped data is a live inventory feed. Confirm rights and allowed use of the source material before production use.
4. Produce an architecture diagram, data ownership map, prioritized gap analysis, risks, migration strategy, and phased implementation plan.
5. Propose minimal changes with file paths and acceptance criteria. Do not perform a wholesale migration without explicit approval.

Business modules and boundaries

Organize Django apps by business responsibility, adapting to what exists:

• accounts: users, identities, sessions, MFA readiness, role assignments, employee status.
• organizations: organization/tenant and branches, with tenant scoping where appropriate. Avoid unnecessary multi-tenant complexity in MVP, but prevent cross-organization access.
• catalog: categories, products, variants, brands, specifications, images, manufacturer documents, synonyms, attributes, source provenance.
• pricing: price lists, currency CRC, tax configuration, price validity, promotions, discount approvals.
• inventory: locations, on-hand quantities, reservations, available-to-promise, adjustments, transfers, stock movements, reconciliation and audit.
• quotations: draft/issued/accepted/expired quotations, line items, versioning, price snapshots, approvals, conversion to orders.
• sales: orders, statuses, fulfillment, returns where in scope; integrate POS/payments later through explicit interfaces.
• warehouse: picking, packing, dispatch, cycle counts, discrepancies.
• logistics: deliveries, assignment, drivers, proof of delivery and route references; do not implement invasive employee tracking by default.
• ai: conversations, permissions-aware tools, agent orchestration, domain guidance, safety policies, evaluation, observability.
• ingestion: source import, normalization, deduplication, image handling, indexing and provenance.
• audit: immutable business event records for sensitive changes.
Keep transactional business rules in Django services, not prompts, serializers, or React.

Frontend experiences

Build role-appropriate, accessible dashboards with clear navigation and shared design primitives:

• Customer: natural-language product discovery, product cards, comparisons, compatible accessories, verified stock by branch, quotations.
• Sales employee: guided product identification, SKU lookup, branch inventory, quotations, substitutes, short technical explanations and visual candidate selection.
• Cashier: permitted order/quotation workflow and payment integration placeholders where needed.
• Warehouse: pick lists, reservations, stock movements, discrepancy workflows.
• Manager: stock exceptions, approvals, sales/operations overviews and staff management.
• Delivery coordinator/driver: assigned deliveries, status updates and navigation handoff, with scoped access.
• Admin: master data, access control, audit and configuration.
Build only the phase-approved screens, but ensure the architecture accommodates these roles.

AI product expert: core behavior

The assistant is not a keyword search engine and not an unconstrained chatbot. It must:

1. Understand the user’s intended project or problem, not just the product word.
2. Recognize colloquial Costa Rican Spanish, technical terms, synonyms, incomplete descriptions, and English/Spanish mixing.
3. Ask only the smallest number of questions that materially affect compatibility, safety or the recommendation.
4. Help users who say “I don’t know” by explaining what to inspect, asking for a photo, or showing real catalog candidate images.
5. Infer candidate product families and search through exact, fuzzy, semantic and structured retrieval.
6. Validate dimensions, materials, ratings, intended use and accessory requirements with trusted specifications.
7. Use real catalog images for product identification. Do not generate images that misrepresent store stock.
8. Recommend necessary complementary components without unnecessary upselling.
9. Explain recommendations clearly and briefly, adapting depth to customer vs employee.
10. Be transparent when information is insufficient or data services are unavailable.

Canonical test scenarios

• “Necesito rodines para una puerta que corre de lado” — distinguish top-hung vs bottom-running systems; ask about load and track when needed.
• “Busco un conector con prensitas/picos y enchufe” — generate hypotheses, search by function/shape/synonyms, show real catalog images and narrow interactively.
• “Necesito pegar un tubo” — establish material, diameter, water/pressure application before recommending adhesive or fittings.
• “¿Tienen este producto?” — catalog existence is NOT proof of stock.
• “¿Cuántos tienen en la sucursal?” — answer only from an authorized, sufficiently fresh inventory lookup.
• “¿Qué breaker necesito?” — avoid unsafe guesses about wire size, load or protection; ask appropriate questions and refer dangerous installation to a qualified professional.

Hard grounding guarantees — enforce beyond prompting

The model must never fabricate store-specific products, SKUs, images, prices, promotions, branch locations, stock counts or specifications. All such claims must be assembled from authorized tool results. Implement backend response schemas that reference existing product IDs, validate IDs and attributes server-side, and render product cards from backend data rather than free-form model text.

Separate catalog state from inventory state. Represent at least on-hand, reserved, sellable/available, location, freshness timestamp and source. Use transactions and row-level locking or equivalent concurrency control for reservations and adjustments. Avoid overselling and race conditions. If a service fails or stock freshness is insufficient, return an explicit UNKNOWN status; never substitute guessed quantities. Maintain provenance and audit for adjustments.

The AI’s read tools must be permission-scoped to the authenticated user and branch/organization. Mutating tools (e.g. create quotation, reserve stock) require server-side validation, idempotency and appropriate confirmation. Never grant the model direct unrestricted SQL execution or database write privileges.

Safety architecture

Safety takes priority over conversion and response speed. Establish domain-specific policies for electricity, gas, structural engineering, chemicals, power tools, pressure systems and other hazardous applications. Distinguish low-risk education from high-risk instructions. Ask for missing safety-critical facts, do not invent specifications, use manufacturer guidance where available, and direct users to qualified professionals for dangerous work. Implement testable policy checks and deterministic validation where possible. Do not rely on a system prompt alone as a safety mechanism. Keep safety guidance contextual and concise.

Product search and ingestion

Create a canonical catalog model separate from raw scraped/imported data. Maintain source URLs, capture time, normalization confidence, image provenance and import job metadata. Normalize units, names, categories, variants, synonyms and local terminology. Detect duplicates without merging distinct sizes or technical variants. Implement searchable structured attributes and filters. Provide import validation reports and reindexing jobs. Do not confuse a public website scrape with authoritative price or stock data. If no inventory integration exists, explicitly show availability as unverified.

Security and privacy

Use least-privilege RBAC and object-level authorization. Enforce organization/branch isolation in Django querysets/services, not just UI. Protect against IDOR, prompt injection from catalog descriptions and uploaded documents, SSRF through URLs, malicious uploads, and unauthorized AI tool calls. Use CSRF-safe auth design, secure cookies where applicable, input validation, rate limits, secrets management, logging redaction, audit trails, and dependency scanning. Avoid storing unnecessary personal information in AI traces. Never expose internal cost data or employee-only fields to customers.

API and UI conventions

Use explicit service contracts, stable pagination, typed errors, filters, idempotency for important writes, and predictable lifecycle states. Frontend must handle loading, empty, stale, unauthorized and failed-tool states. Use streamed AI responses only where it materially improves UX, and ensure the final product references are independently verified. Implement responsive product cards with images, SKU, price, stock status/freshness, compatibility notes and branch context, but show fields only when authoritative data exists.

Evaluation and testing

Create automated tests for:

• Unit tests for inventory math, pricing, reservations, quotations and permissions.
• Integration tests for catalog search, stock tools, branch scoping and AI endpoints.
• Concurrency tests preventing overselling.
• Prompt-injection tests against untrusted product descriptions and imported content.
• AI behavior evaluations covering ambiguity, local vocabulary, tool failures, safety, visual candidates, missing accessories, nonexistent SKUs, stale stock and zero stock.
• End-to-end customer and employee journeys.
Track grounded-product precision, search recall, compatibility errors, unsupported inventory claims, unsafe responses, unnecessary questions, tool latency, token usage and task completion. Treat unsupported inventory or fabricated products as release-blocking failures.

Phased delivery

Phase 0 — Repository inspection, gap analysis, architecture decision records and migration plan.
Phase 1 — Django foundation, auth/RBAC, product catalog normalization, typed APIs and Next.js shell; preserve existing behavior.
Phase 2 — Exact/fuzzy/hybrid search, synonyms, candidate product cards and import pipeline.
Phase 3 — Inventory truth, branch stock, reservations, freshness, concurrency controls and audit.
Phase 4 — AI sales copilot with safe tools, clarification loops, expert domain policies and evaluations.
Phase 5 — Employee-assisted sales, quotations, compatible accessories, product comparison and visual identification.
Phase 6 — Warehouse and fulfillment workflows; then delivery operations.
Phase 7 — Management analytics, multi-organization hardening, performance, observability and production readiness.
Reorder only with a documented rationale grounded in the existing repository.

Cost and performance discipline

Prefer PostgreSQL-native capabilities before adding separate search infrastructure. Use small model calls with narrowly retrieved context; cache only non-sensitive, appropriately versioned data. Batch embeddings and run ingestion asynchronously. Measure actual latency and cost before adding additional agents, vector databases, queues or services. Prefer specialist instructions/tools over multiple always-on agents unless evaluations show a benefit.

Working method in Claude Code

1. Inspect the repository and report what exists; do not guess.
2. Produce a requirements-to-existing-code matrix with COMPLETE / PARTIAL / MISSING / UNSAFE.
3. Recommend a target architecture and exact module/file changes.
4. Write an incremental, prioritized plan with acceptance criteria and rollback strategy.
5. For each approved phase, implement a small vertical slice, add migrations and tests, run lint/typecheck/test suites, and report results.
6. Never claim a test passed unless executed. Never claim a tool/data integration exists unless verified.
7. Do not fabricate products, stock or pricing in demos without explicitly labeled synthetic fixtures.
8. Stop and ask for a decision before destructive migrations, large rewrites, production changes, or unapproved infrastructure cost.
