## Limitations and next action

- Django 6.0 (not 6.1) because drf-spectacular and released pytest-django do not yet declare 6.1 support; 6.0 extended support ends April 2027 (upgrade trigger in ADR 0002).
- Host Python is 3.13.0 (old patch). Host ruff/mypy pass, but the container (3.13.17) is the reference test runtime. Updating the host interpreter is an owner action.
- `node_modules` on the host was installed by the Linux/musl container. Host Node 20 is not supported for these tools; a host Node 24 needs a fresh `npm ci`.
- npm 11.19.1 reports `unrs-resolver@1.12.2` postinstall as not covered by `allowScripts`. The script was not approved; lint works through the prebuilt optional native binding. No `.npmrc` was added (outside the assigned files).
- `SECURE_PROXY_SSL_HEADER` is off by default (`DJANGO_TRUST_PROXY_PROTO_HEADER=0`) because local runs over plain HTTP. `X-Forwarded-Host/Port` are never trusted. Django has no published port, so only the proxy (and the web container on the internal network) can reach it.
- The web container serves a production build (no hot reload). Developer hot reload, server-side fetch helpers (`API_INTERNAL_URL` is already set) and the generated client belong to P1-03.
- The custom error envelope, request_id, throttling, `Cache-Control`/`Vary` and CSRF endpoint are not implemented here (P1-02A/B). DRF defaults are set to JSON-only, SessionAuthentication and IsAuthenticated.
- No CI configuration was created (requires owner review).
- Built images `hwp1check-*` and `hwp1fix-*` remain in the local Docker image cache (no containers or volumes). Remove them with `docker image rm` if you want.
- Next action: coordinator review, then hand `apps/api/config/` to P1-02A and the web placeholder to P1-03.
